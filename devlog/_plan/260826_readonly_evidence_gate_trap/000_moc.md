# Read-only subagent cannot record evidence — the gate traps it forever

## The report

"readonly로 보냈을때 기록을 못하는 문제" — a subagent dispatched read-only cannot
record its evidence, and the session never ends.

## The reproduction (from a real transcript)

A `agent_type:"worker"` child was dispatched with a scratch-only write scope
(`/tmp/ocx-s1-jobZ09`). It completed its task correctly. Then:

1. It answered with `EVIDENCE_RECORDED: .codexclaw/evidence/probe_receipt.txt`.
2. `hasValidReceipt()` resolved that against the PARENT cwd, found nothing, returned false.
3. The gate blocked with `verifierDirective(1)`, then `(2)`, then `(3)`.
4. At `attempts >= MAX_ATTEMPTS` it switched to `escalationDirective()` — and returned
   that same block on EVERY subsequent SubagentStop.

The transcript shows 15+ consecutive identical escalation blocks. The child kept
re-emitting the same report; the gate kept refusing. There is no exit from that branch.

## The two defects

**D1 — the escalation branch is not terminal-bounded.**
`subagent-evidence.ts:197-199`: once `attempts >= MAX_ATTEMPTS`, every call returns
`{decision:"block"}`. Nothing decrements, expires, or releases. `clearAttempts()` runs
only on a VALID receipt — which is precisely what the trapped child cannot produce.
The loop is unbounded by construction.

**D2 — a read-only child is asked for a write it cannot perform.**
The receipt must be a real, non-empty, non-symlink file inside the parent's
`.codexclaw/evidence/`. A child sandboxed away from that path can never satisfy it,
so D1's cap is reached with certainty rather than by accident.

## What the research settled

Three read-only lanes (evidence under `.codexclaw/evidence/260826_readonly_gate_*.md`):

- **Provenance:** `permission_mode` IS reliably delivered on SubagentStop, but it is
  derived from approval policy and only ever emits `default` or `bypassPermissions`.
  `readOnly` is not even in the hook schema enum. **A fix keyed on `permission_mode`
  would be a no-op.** No payload field reports filesystem writability. The hook process
  runs with the PARENT's credentials, so probing writability cannot classify the child.
- **Prior art:** the original LazyGap contract explicitly specified "block up to
  MAX_ATTEMPTS then RELEASE" so the gate could never trap a session. A later
  security-hardening pass reversed it to permanent fail-closed escalation. This is a
  real policy conflict to resolve deliberately, not a typo to silently patch.
- **Release:** 12 version surfaces move together; `check-versions.mjs` misses
  `cli/` and `gui/`. Local deploy is `codex plugin add` keyed on the manifest's
  `+codex.<stamp>` cachebuster.

## The resolution (after 3 audit rounds)

Restore bounded termination WITHOUT restoring fail-open. At the cap the gate records an
unresolved TOMBSTONE into the session State and releases the child. The already-shipped
`GOAL-COMPLETE-GATE-01` then denies `update_goal{status:"complete"}` while any tombstone
is unresolved. The child regains liveness; the parent inherits the fail-closed verdict.

Two designs were proposed and killed by audit before this one:

- a hook-authored artifact in a new `evidence-unverified/` directory — a child could
  pre-create that directory as a symlink to `evidence/` and turn the artifact into a
  valid receipt;
- a `dispatch-capability` marker file — the hook and child run as the same host user,
  so the child could forge its own read-only declaration.

Neither survives. The tombstone lives in session State, which is not a child-designated
destination, and no new trusted input is introduced anywhere.

The premise behind the audit's central objection was then falsified by experiment
(005): one junk byte already releases a worker on call 1, so bounded release opens no
new opt-out. Final verdict NEAR-PASS.
