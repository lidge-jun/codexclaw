## 2. 머지 순서와 그 이유

```
#100 → #102 → #106
       #105 → #108
       #103 → #107

```

### 2.1 스택 제약 — dependent base를 못 썼다

이 레포는 `enforce-pr-target` 워크플로가 모든 PR의 base를 `dev`로 강제한다. GitHub의 dependent
base 스택(위 PR의 base를 아래 PR의 head로 두는 방식)을 쓰면 그 검사에 걸린다. 그래서 스택을
**로컬 브랜치 체인 + 전 PR `dev` 타깃 + 머지 순서**로 대체했다.

결과로 #106·#107·#108의 diff에는 각자의 base 브랜치 커밋이 함께 보인다. 아래 PR을 먼저 머지하면
위 PR은 자기 커밋만 남는다. #106·#107·#108 본문에 이 사실을 각각 적어 두었다.

### 2.2 순서의 근거

- **#102 → #106**: 순서 자체가 논증이다. `managed-keys.ts`의 caution 문구가 "명시 요청 없는 쓰기를
  막는 장치를 먼저 확인하라"를 요구하고, #106은 그 장치가 #102라고 주장한다. 역순으로 들어가면
  정당화가 성립하지 않는 기간이 생긴다. 되돌릴 때는 반대로 #106을 먼저 되돌린다.
- **#105 → #108**: `memory-search.ts`를 공유한다. #108의 스코핑 코드가 #105의 `query-words.ts`
  분리 위에 서 있다.
- **#103 → #107**: `index-db.ts`를 공유한다. #107이 `recall_hit_counts`를 #103의 스키마 위에 얹는다.
- **#104는 독립**: `recall/src/hook.ts`·`cwd-context.ts`를 다른 갈래와 공유하지 않는다. 다만
  `recall/dist/*.js`는 여러 갈래가 함께 만드는 생성물이므로, 머지 충돌이 나면 손으로 풀지 말고
  base를 머지한 뒤 `npm run build`를 다시 돌려 커밋해야 한다. 손으로 풀면 `dist-freshness`가 깨진다.

## 4. 로드맵과 달라진 점

각 구현 보고에서 나온 것을 모은다. 로드맵이 틀렸다기보다, 구현이 로드맵보다 한 겹 아래를 봤다.

### #102 (wp1-A)

- **훅 개수 결합이 12표면이다.** 로드맵이 6표면을 열거했고 감사가 11로 늘렸는데, 구현 중
  `cxc-ops/test/manifest-targets.test.ts:245`가 `pabcd-state/dist/cli.js`를 가리키는 훅 개수를
  하드코딩해 두어 실패했다. 그게 12번째다. 의도적으로 심어 둔 트립와이어가 작동한 셈이다.
- 12표면 중 둘(`how-it-works.md:36`, `plugin-manifest.md:19`)은 `Twenty-three` 영문 스펠아웃이라
  숫자 grep으로 안 걸린다. `index.mdx:151`은 이벤트별 분포까지 적고 있어 `PreToolUse x6`을 `x7`로
  함께 고쳤다.
- **첫 idiom 패턴이 너무 넓었다.** 초안이 평범한 엔지니어링 프롬프트의 `store.mjs`나 `test/notes`에
  걸려 `hook.test.ts:194`의 중립 비-발동 대조를 깼다. 패턴을 "메모리에" 같은 목적지 명시 요구로
  좁혔다. 그 대조 테스트가 정확히 이걸 잡으려고 있던 것이다.

### #103 (wp5-A)

- **기본 정렬을 관련도로 바꿨다.** 로드맵은 K 확대의 지연 회귀를 우려해 기본을 시간순으로 두려
  했다. 측정 결과 랭킹 경로가 기존과 동등해서(`opencodex release` 369ms vs 356ms, `ci` 137ms vs
  110ms) 그 유보를 풀었다. `--recent`가 이전 동작이고 `--rank`가 명시형이다.
- **recency 항의 첫 크기가 30배쯤 컸다.** `0.5/k`로 잡았더니 한 시간 전의 스치는 언급이 30일 된
  밀집 매치를 눌렀고 테스트 넷이 잡았다. BM25 레인 선두의 인접 랭크 간격 하나로 줄였다.
- **레인 소속은 매칭 판정이 아니다.** FTS 토큰화가 스캔 경로의 substring 규칙보다 거칠어서, 레인에
  들어왔지만 스캔 의미로는 매치가 아닌 행이 나온다. 후보를 JS에서 재검사한다. SQL에서 trigram
  `MATCH`를 다시 돌려 검증하면 실측 250ms가 붙는데, JS 재검사가 그 비용도 없앴다.
- `index.test.ts`의 오라클이 스캔 경로와 **순서까지** 비교하고 있어 매칭과 랭킹을 뒤섞었다. 계획된
  파일 집합 밖의 변경이고, recency 모드에서 스캔 동등성을 고정하고 랭킹에서는 집합 동등성을 본다.

### #104 (wp4)

- **compacted 예산이 `{chars: 600, topN: 2}`로는 성립하지 않는다.** 신선도 라벨을 포함한 프레임만
  471자다. 100자 발췌 둘이면 704자 근처라 문자 상한이 먼저 걸려 조용히 한 세션으로 잘리고, `topN`이
  아니라 문자 수가 구속 조건이 된다. 로드맵의 자체 추정치 약 670도 이미 600을 넘겼다. 상한을 800으로
  두고 `topN`이 먼저 구속한다는 것을 테스트로 고정했다.
- 봉투 전체 크기를 비교하는 테스트를 직접 비교로 바꿨다. 봉투에는 뒤따르는 포인터 문구가 들어가는데,
  compaction 쪽 문구가 정당하게 더 길다.
- 밀도 증가 전에 **줄 단위 예산 누적**을 먼저 넣었다. 기존 렌더러가 통짜 문자 절단이라
  `</untrusted-recall-data>` 닫는 태그를 자를 수 있었다.
- 발췌 추출이 `<recommended_plugins>`를 건너뛴다. 그게 `SYNTHETIC_PREFIXES`에 없어서 많은 세션의
  "첫 메시지"가 돼 버린다.

### #105 (wp2)

- **계획에 없던 완화 재시도를 넣었다.** 경계 매칭만으로는 코퍼스가 `PR3956`으로 적은 것을 `3956`
  질의가 못 찾는다. 조용한 0건이 라벨 붙은 약한 결과보다 나쁘다고 보고, strict 통과가 0건이면
  무경계로 재시도하되 커버리지 1단위를 감점하고 `lower confidence` 경고를 붙인다.
- **어미 절단이 계획된 조사 목록을 넘어 하-계열 활용까지 간다.** 로드맵 자신의 검증 질의
  `왜 그렇게 결정했지`가 그걸 요구한다. `했지`는 조사가 아니고 시제·서법 어미는 열거가 불가능하다.
  두 음절 어간 규칙이 위험을 묶는다 — `이해`·`오해`는 한 음절 어간이 남아 기각된다.
- **stage1 SQL prefilter는 substring으로 남겼다.** SQL에는 커스텀 collation 없이 단어 경계가 없다.
  `LIKE '%w%'` prefilter는 그대로 두고 행 본문에서 경계를 재검사한다.
- `rollout.ts:192`와 `chat-search.ts:94`는 의도적으로 안 건드렸다. chat search의 인덱스 경로가 trigram
  `MATCH`로 단어를 푸는데, 스캔 의미만 바꾸면 `test/index.test.ts:46`의 인덱스/스캔 동등성 오라클이
  깨진다. 이유를 코드에 적었다.

### #106 (wp1-B)

- **관리 키 규칙의 범주를 바꿨다고 주장하지 않는다.** `memories.dedicated_tools`는 여전히 "codexclaw
  없이도 의미 있는 키" 판별식을 통과한다. 논증을 좁혀서, caution 문구가 지목한 잔여 위험(모델이
  자발적으로 `extensions/ad_hoc/notes/`에 남기는 노트) 하나에 #102의 게이트가 대응한다고 적었다.
  반론(codexclaw를 지우면 게이트만 사라진다)도 주석에 남겼다.
- 목록 소속이 자동 활성화를 뜻하지 않도록 `autoEnable`을 평범한 불리언으로 만들고
  `autoEnabledManagedKeys()`로 부분집합을 명시했다. 자격을 갖춘 항목이 정확히 하나임을 테스트가 본다.
- **prior value를 스냅샷에서 읽는다.** `codex features enable`이 `config.toml`을 다시 써 버리므로,
  건드리기 전에 찍은 스냅샷에서 이전 값을 읽어야 부재/`false`/사용자가 이미 `true` 세 경우가 구분된다.
  쓰기는 feature 패스 뒤에 놓았다.

### #107 (wp5-B)

- 로드맵과 크게 다르지 않다. `index-db.ts`에는 저장소(`hitCountRef`, `readHitCounts`, `bumpHitCounts`)만
  들어가고 비용 계산을 모른다. `chat-search.ts`·`index-search.ts`·`memory-search.ts` 어느 쪽도 이를
  부르지 않아 명시 검색의 결정론이 구조적으로 유지된다.
- 감사 §5-4가 지적한 감점 단위 근거 문제는, 후보가 한 자리씩 떨어져 도착한다는 사실로 다시 썼다.
  `(count - threshold + 1) * 0.5`가 리스트 위치로 직접 읽힌다 — 0.5는 반 칸이다.
- 테이블이 없을 때 랭킹이 중립으로 돌아가는지를 테스트가 확인한다. `openIndexReadOnly`가 스키마를
  만들지 않으므로 읽기 경로는 부재를 견뎌야 한다.

### #108 (wp3)

- **frontmatter 파싱을 선두 블록으로 한정했다.** 계획된 `/^cwd:/m`은 `raw_memories.md`를
  `/Users/jun`으로 오라벨한다. 그 파일이 스레드별 블록 448개를 이어 붙인 것이라 첫 블록의 `cwd`가
  파일 전체를 대표해 버린다. `rollout_summaries` 256건은 어느 쪽이든 같다.
- 산문 언급(`applies_to: cwd=…`)에 절반 보너스를 준다. 구조화된 `cwd`만 보면 `--cwd-only`가
  `MEMORY.md`를 통째로 버리는데, 정작 프로젝트 규칙이 거기 있다.
- **순환 import는 이미 없었다.** #105의 `query-words.ts` 분리가 런타임 간선을 제거했고, `import type`은
  타입 스트리핑 빌드에서 완전히 지워진다는 것을 확인했다.
- `--no-tools`를 재사용하지 않았다. 그 플래그는 chat search 사용자 것이고 의미가 겹친다. 보완 경로는
  항상 `includeTools: false`로 돌고, `--no-chat`이 보완 자체를 끈다.

## 5. CI가 잡은 결함

로컬에서 못 잡고 CI가 잡은 것이 두 종류다.

**(1) 테스트 총계 배지 결합.** README 3종이 테스트 총계를 배지로 싣는다. 이 워크트리에는
`gui/node_modules`가 없어 `gui/test/router.test.ts`가 `react`를 못 찾고 실패하며, 그래서 로컬 총계가
CI보다 1건 적게 나온다. 브랜치 여섯 개에서 배지가 어긋났고, 각 브랜치 끝에 CI 실측값으로 맞추는
커밋(`Publish the test count …`)을 따로 붙여야 했다. 로컬 수치를 그대로 쓰면 매번 깨진다.

**(2) windows 전용 `path.resolve` 버그.** #108의 cwd 비교가 `path.resolve`를 거쳤는데, windows에서
이 함수가 POSIX 경로의 슬래시를 백슬래시로 바꾼다. 비교 대상 한쪽만 변환되니 cwd 일치가 전부
`false`가 되어 windows 잡이 실패했다. 양쪽을 같은 형태로 만드는 `normalizeCwd` 대칭 정규화로 고쳤고
(`409eb693`), 최종 head `e5cf1c49`에서 windows 잡 셋이 통과한다. macOS·리눅스 로컬에서는 절대 재현되지
않는 종류의 결함이다.

## 6. 남은 것 / 확인 못한 것

- **compaction 후 SessionStart(`source=compact`) 발화의 런타임 실증.** c-8 (ii)가 여기 걸려 있다.
  실제 compaction을 유발한 세션에서 훅 발화를 관찰하지 못했다. 소스 경로와 CLI 직접 호출까지가 근거다.
- **인덱스 신선도 — `--no-refresh`.** 훅은 `--no-refresh`로 질의하므로 마지막 ingest 이후에 만들어진
  워크트리는 #104의 cwd 열거 수정과 무관하게 계속 0건이다. 실측으로 이 워크트리의 `files` 행이 0건이고
  `meta.last_ingest_at`이 세션 생성보다 앞선다. #104는 이 문제를 보고만 하고 고치지 않았고, 커버리지
  수정은 실제 ingest 경로로 만든 픽스처 인덱스에서 증명했다.
- **`--cwd-only` 0건 지연 2.7초.** chat search의 기존 `--cwd` 필터가 느린 인덱스 경로를 타는 데서 온다.
  #108이 만든 문제가 아니고 #108이 고치지도 않았다. `--cwd` 부스트는 140ms 근처다.
- **chat search의 후행 슬래시 `--cwd`가 0건.** 기존 문제이고 이번 범위에서 건드리지 않았다.
- **self-heal `healedKeys` 확장.** 마켓플레이스 설치 경로에 table-key를 태우려면 마커 스키마 확장이
  필요하다. 처음부터 범위 밖으로 선언했고 그대로다. 독립적으로 되돌릴 수 있는 별도 변경이어야 한다.
- **`memoriesadd_ad_hoc_note` 훅 stdin 실측.** #102의 matcher는 네임스페이스 유무와 구분자 형태를 모두
  받는 방어형이라 게이트 자체는 안전하지만, 실제 덤프로 이름을 확인하지는 않았다.
- **어미 절단의 정밀도 손실.** 부착률은 코퍼스 통계로 쟀지만 전후 상위 5건 품질 비교는 골든 셋이
  있어야 한다.

## 7. 후속 제안

로드맵 P2/P3 중 이번에 안 한 것과 각각의 착수 조건이다.

| 항목 | 내용 | 착수 조건 |
|---|---|---|
| P2-2 | 회수 다양화 — 파일/스레드당 상한 | #107의 hit-count 감점이 머지된 뒤, 그럼에도 한 스레드가 상위를 독점하는 관찰이 나오면. 감점과 상한은 같은 증상의 다른 처방이라 둘 다 넣기 전에 하나의 효과를 봐야 한다 |
| P2-4 | 회수 실행 이력 로그(메타데이터만, 크기 상한) | "자동 주입 발동/빈 결과" 비율을 실제로 세고 싶어질 때. 지금은 그 수치가 없어 밀도·감점의 효과를 논증으로만 판단한다. 432MB 부풀림 전례가 있으므로 상한 설계가 선결 |
| P2-5 | chat search 동의어 확장(opt-in `--synonyms`) | chat search가 동의어를 안 쓰는 이유가 코드·주석·테스트 어디에도 없다. 그 근거를 먼저 찾거나, 없다는 것을 확정한 뒤에. 기본 off 유지 |
| P3-1 | PABCD phase 인지 회수 | 주입 내용이 phase별로 달라져야 할 실제 사례가 나오면. 하드코딩 규칙이 아니라 쿼리 차이로 구현될 수 있는지가 판단 기준 |
| P3-2 | 검색 힌트 추출(고유 식별자 제시) | LLM 호출 없이 구현 가능한 설계가 나오면. 힌트가 실제 후속 검색으로 이어지는지를 P2-4의 로그로 확인할 수 있게 된 뒤가 낫다 |
| P3-3 | memory search 인덱스화 | **200ms 초과**. 이번 실측이 `--cwd` 부스트 140ms 근처라 아직 아니다. 단 `--cwd-only` 0건의 2.7초는 별개 경로이고 그건 chat search 필터 쪽에서 봐야 한다 |
| P3-4 | PABCD 완료 사이클 → ad_hoc 노트 | **사용자 승인 선행 필수.** "명시적 사용자 요청"과 "PABCD Done 도달"을 같게 볼 것인지가 미결이고, 그 결정 없이는 착수하지 않는다. 안 할 수도 있는 항목이다 |

이번 사이클이 P3-4의 전제 하나는 만들어 뒀다. #102의 게이트가 "명시적 요청"을 세션 마커와
`cxc memory allow-write`라는 두 형태로 실체화했으므로, PABCD Done을 그 요청으로 볼지의 논의가
추상론이 아니라 구체적인 승인 경로 하나를 추가할지의 문제가 된다.
