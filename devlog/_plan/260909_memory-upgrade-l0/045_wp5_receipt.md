# 045 — wp5 인도 영수증

wp5 = chat search 랭킹(P2-1)과 hit-count 감점(P2-3). [PR #103](https://github.com/lidge-jun/codexclaw/pull/103), [PR #107](https://github.com/lidge-jun/codexclaw/pull/107). 최종 head CI 각 pass 10 / fail 0.

## 해법이 이미 스키마에 있었다

`msgs_fts`(unicode61)는 인덱스 스키마가 쓰인 이래 생성되고 트리거로 동기화돼 왔는데 어디서도 쿼리되지 않았다. BM25 준비가 끝난 314,426행이 그냥 놓여 있었고 `index-search.ts` 는 trigram 레인과 recency 스캔만 만졌다.

두 레인이 중복이 아니라 상보적이라는 근거는 실측이다. `ci` 질의에서 trigram 은 0행, FTS 는 65,171행을 준다. 단어 내부 부분문자열에서는 반대가 성립한다.

## recency 항의 크기는 고른 게 아니라 유도했다

첫 시도 `0.5/k` 는 약 30배 과대였다. 한 시간 전의 스치는 언급이 30일 전의 밀도 높은 매치를 이겼고 테스트 4개가 잡았다. BM25 레인 선두의 인접 순위 간격 정확히 하나로 맞추면, 신선도가 비슷한 매치들 사이를 가르되 두 레인 모두에서 앞선 히트를 뒤집지는 못한다.

## 레인 소속은 매치 판정이 아니다

FTS 토크나이제이션은 스캔 경로의 substring 규칙보다 거칠다. 그래서 레인 후보를 JS 에서 스캔 의미로 재검사한다. 이 재검사가 성능 해법이기도 했다 — SQL 에서 trigram `MATCH` 를 다시 도는 비용이 실제 인덱스에서 약 250ms 였다. recency 스윕을 레인이 페이지를 못 채울 때만 도는 top-up 으로 바꾼 것과 합쳐 지연이 동등해졌다: `opencodex release` 369ms 대 356ms, `ci` 137ms 대 110ms, 한국어 질의는 오히려 빠르다.

## 기본 정렬

관련도를 기본으로 두고 `--recent` 로 기존 목록을, `--rank` 로 명시적 관련도를 남겼다. 계획은 지연 회귀 위험 때문에 시간순 유지를 기본으로 하려 했는데, 측정이 그 위험을 제거했다.

회수 훅의 자동 주입만은 시간순으로 못박았다. 스레드별 최근 작업을 요약하는 자리이므로 명시 검색의 기본값을 물려받으면 안 된다.

## hit-count 감점은 자동 주입 전용이다

`demoteRepeats` 가 `hook.ts` 안에만 있고, `index-db.ts` 는 저장(`hitCountRef`/`readHitCounts`/`bumpHitCounts`)만 제공하며 카운트가 얼마의 비용인지 모른다. `chat-search.ts`·`index-search.ts`·`memory-search.ts` 어디서도 호출하지 않으므로 CLI 로 노출될 플래그 자체가 없다. 같은 질의를 반복하는 사용자는 같은 답을 받는다.

후보가 한 자리씩 떨어져 도착하므로 jawcode 공식 `(count - threshold + 1) * 0.5` 가 목록 위치로 그대로 읽힌다. 0.5 단위는 반 자리이고, 무료 임계 3회를 여러 번 넘겨야 실제로 자리를 잃는다. 지금 하고 있는 작업이라서 매번 올라오는 스레드를 벌하지 않기 위한 여유다.

## 스키마 버전은 움직이지 않는다

`INDEX_SCHEMA_VERSION` 은 `"2"` 그대로다. base 대비 diff 에 대입문 변경이 없고, 컴파일된 `dist/index-db.js` 도 `= "2"` 이며, 테스트가 상수와 함께 실제 인덱스의 `meta.schema_version` 및 `recall_hit_counts` 존재를 확인한다. 나중에 누가 올리면 12GB 재파싱이 조용히 도는 대신 테스트가 깨진다.

테이블을 지우면 랭킹이 중립으로 돌아온다. `openIndexReadOnly` 가 스키마 문을 돌리지 않으므로 두 접근자가 없는 테이블을 빈 이력으로 취급한다. 쓰기도 경계가 있어 주입이 비어 있지 않다고 확정된 뒤에만 기록하고, 페이지에 오른 다섯 스레드만 과금한다.
